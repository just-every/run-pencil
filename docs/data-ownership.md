# Action reminder custody

ACT-009 uses the existing minute cron and Base email sender. It adds no inbound mail handler or external connection. Email contains the operator-written action title, review date and authenticated action link; it contains no response text, respondent identity or access token. NOTIFY-004 applies: the configured no-reply sender and Auto-Submitted: auto-generated are required. Operator reminder failures are retained in the action reminder ledger and do not mark any participant bounced.

Migration 0054 is additive to v0.7.0: every existing action and dependent row remains. It adds action-level reminder eligibility, an action_reminders outbox unique by action, kind and due calendar date, and action_reminder_attempts. Calendar dates use the workspace zone. Before means three calendar days before review; an action created during that lead period can receive its before reminder immediately. The review date and each seventh day after it create their own occurrence. The cron materializes due work before checking sending hours; deferred occurrences remain pending until the WS-002 window opens. Catch-up preserves occurrences in chronological order. Permanent failures and ambiguous transport outcomes are visible and never automatically replayed; confirmed rate limits retry at most five times, held for sending hours when necessary.

An operator verdict, closure or review-date change cancels pending/in-flight old schedule work; owner changes move unattempted queued work to the current owner and cancel already attempted work in the action update transaction. Immediately before transport the sender checks current action eligibility, current owner identity/email, departed-operator status and current sending hours. An already accepted message cannot be recalled. No reminder writes a verdict. A missing/departed owner or missing address sends nothing and is explained on the action. Actions with no owner retain pending history without sending it.

The action and reminder tables hold private operator data. Reminder rows reference their action with ON DELETE CASCADE; attempt rows cascade from their reminder. Owner deletion anonymizes the reminder operator reference. Anonymized action.reminder audit entries retain only the feature, time and status, with no action ID, recipient, title or provider receipt. Action erasure removes reminder and attempt rows; audit history survives.

Local, hosted and browser archives use scripts/deployment-data-policy.mjs. Every reminder and attempt field is retained, including idempotency keys, statuses, attempts and provider receipts. The actions.reminders_enabled field is exported as 0, so restoring/re-exporting remains equal and restoring never sends queued or newly generated reminder mail for historical actions. The action page explicitly reports that restored reminders are paused. Credentials and private connection settings remain excluded by the existing policy. New actions retain normal scheduling. This recovery guard is distinct from an additive software upgrade, which leaves existing actions eligible and retains every row.

Only the existing email channel ships. INTEG-006 must inherit this owner reminder schedule, sending-window deferral, verdict cancellation and no-loop obligation when Slack/Teams connections exist. INTEG-013 must implement linked task status readback/display/refresh; no task status is inferred from delivery success and no reminder sets Pencil's verdict.
