# Hosting Pencil

rer installs the pinned Node and pnpm itself. Install with `rer install`, qualify the exact source with `rer verify` and run `pnpm run verify:release` before release. `pnpm run deploy -- --dry-run` validates the real Worker/assets/migrations and owner declaration with zero provider requests.

Actual `pnpm run deploy -- --environment production` requires the intended Cloudflare account/API token and production MAIL_FROM and MAIL_API_KEY. Set OWNER_EMAIL to the hosted owner’s email and pass it with `SEED_ADMIN_EMAIL="$OWNER_EMAIL" rer deploy --environment production`; Pencil’s current declaration reads SEED_ADMIN_EMAIL. rer generates fresh hosted SESSION_SECRET and one-time SETUP_TOKEN values when omitted. An explicitly supplied SESSION_SECRET must have at least 32 characters; preserve the deployed value across updates. Supply them privately through the authorized deployment environment, never argv or output. `PENCIL_MAIL_PROVIDER` selects `sendgrid` (the default) or `resend`; the earlier `MAIL_PROVIDER` environment setting is accepted when it agrees. The deploy adapter passes this through the published kit as the Worker’s `MAIL_PROVIDER` binding. Choose it and the matching `MAIL_API_KEY` before the first deploy. For an existing released Worker whose provider is a plain variable, the adapter reads and preserves that provider while the kit inherits its opaque API key; a conflicting explicit provider is refused. Once provider and key are both secrets, subsequent deployments inherit them rather than rotate them. deploy.json selects production mail, derived resource identities, scheduled maintenance, ordered D1 migrations and public origin; local capture and sample data are disabled. A healthy Worker does not prove real mail delivery or hosted capacity.

After a healthy first deploy, rer automatically claims the hosted owner through native Base authentication, removes SETUP_TOKEN and records the new Worker version. Once deploy confirms success, the owner signs in by email at `/signin` and finishes `/setup`; no manual setup-token claim is needed. Preserve owner data and opaque existing provider secrets. Export before upgrades, verify restore into an empty database and retain a compatible deployment until owner acceptance. Never replay mail in recovery. Hosted managed admission requires owner proof; a private push or dry run installs nothing. Tags, public publication and site listing are separate owner actions after full release verification and a zero-finding scan.

After successful automatic owner claim and token retirement, unset SETUP_TOKEN in the calling environment. Repeat deployments keep the existing owner and secrets without uploading the retired token. If claim or retirement fails, follow the CLI’s recovery instructions with the same environment credentials. An initialized installation refuses another owner claim. Do not mutate Worker secrets in the dashboard: rer treats that new Worker version as `owned-resource-replaced`. Keep and privately back up `.rer/deploy/<environment>.json`; do not edit it to bypass the refusal. A Worker already changed outside rer requires the deploy kit’s supported ownership recovery.

This hosting path requires Workers Paid and uses its default 30,000 ms request CPU budget; Workers Free’s 10 ms limit is a different service tier. Pencil being free software does not select a free provider plan. rer 0.2.1 rejects `limits.cpu_ms` in the owner declaration and emits no CPU limit in upload metadata, so an explicit per-Worker budget requires a future supported deploy-kit contract. Consult [Cloudflare’s limits](https://developers.cloudflare.com/workers/platform/limits/).

Hosted upgrades from released 0.2.0 remain blocked with rer 0.2.1: its hash ledger refuses the changed `0019_import_custody.sql` before any upgrade writes or migration 0034. The name-based Workers D1 upgrade proof does not cover this kit path. Retain the existing source and database, and use only a supported matching-version backup path until Base provides a maintained, reviewed released-hash transition contract that retains the actual applied history and applies the additive convergence migration. Do not rewrite ledger hashes, bypass checks, switch migration controllers or assume export/restore qualifies this transition. This source’s deployed recovery CLI also checks migration hashes and does not establish export compatibility with the old 0019 history. Fresh installation and provider preservation are separate proofs; neither establishes a supported 0.2.0 hosted upgrade.
